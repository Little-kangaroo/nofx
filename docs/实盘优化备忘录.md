## 四、关键参数调优决策树

### 4.1 开仓率

```
如果开仓率 < 10%（每天少于1笔）：
  → 检查 OF_STALE 频率（target: <20%）
  → 检查 WEAK_SIGNAL_FILTERED 频率（target: <30%）
  → 检查 NO_TRIGGER_FOR_DIR 频率（target: <15%）
  → 可考虑降低 ThetaNeutral: 0.15→0.12
  → 可考虑降低 MinConf: 0.40→0.35

如果开仓率 > 40%（每天超过4笔）：
  → 检查是否有太多 borderline 交易（胜率<55%）
  → 考虑提高 ThetaNeutral: 0.15→0.20
  → 考虑提高 borderline_min: 0.45→0.55
```

### 4.2 胜率

```
如果整体胜率 < 50%：
  P0：立即暂停，分析失败模式
  → 检查 direction_confidence 分布：低置信度(<0.70)交易胜率如何？
  → 检查 struct_dir 与 of_dir 冲突的交易（ABSORPTION_HINT + SHORT）
  → 检查 DIVERGENT_MIXED 的交易胜率（降级0.5×macroSign是否有效）

如果胜率 50-55%（EV 接近0）：
  → 专注于提高 RR，而非胜率
  → 检查 HTF_swing 的 RR 是否被低估

如果胜率 > 60%（好于预期）：
  → 可适当降低 rr_min 增加开仓机会
  → borderline 可放宽到 rr_min=0.60
```

### 4.3 按 coin 分析

```
如果某个 coin 胜率持续 < 45%（至少10笔）：
  → 检查该 coin 的 OF_STALE 频率
  → 检查是否流动性不足（spread 成本吃掉 RR）
  → 考虑从候选列表移除该 coin

如果 BTC 始终 OF_STALE：
  → 检查数据管道：orderflow status 是否频繁非"正常"
  → 考虑调整 BTC 的 MinOverallScore 单独配置
  → 或放宽至 MinOverallScore=0.55（仅 BTC）
```


```
3. Gate4 PASS（有触发器）
4. market_regime = trend：
   a. 4h Channel.direction ∈ {up, down}，且 current_position ≠ {middle, inside} 或

   c. 4h/1h 道氏结构 HH+HL（多）或 LH+LL（空）
5. pattern ∈ {BO_RETEST, EDGE}（非 ENGULF / MOMENTUM_BREAK）
```

**最常见阻断点**：

| 阻断条件 | 诊断方法 | 调优方案 |
|---------|---------|---------|
| market_regime ≠ trend | AI reasoning 中检查 market_regime 判断 | 放宽判定：SupertrendDir 单独满足即可 |
| R_clean_eval < 1.5 | Gate5 输出中找 R_clean_eval 值 | 检查 Anchor1 目标是否过近 |
| pattern = ENGULF（非 BO_RETEST/EDGE） | trigger_primary 是否总是 ENGULF 类 | 无法直接修改；需要等 BO_RETEST 触发 |
| Gate4 HTF_BREAKOUT_AGAINST_DIR | 4h channel break_up 且 pattern 非 SFP/ENGULF/EDGE(q≥0.90) | 已部分修复；如仍阻断检查 q 阈值 |

```python
at_support_break = [t for t in short_trades if 'BO_RETEST_BEAR' in t['trigger_flags']]
below_support = [t for t in short_trades if 'ENGULF_BEAR' in t['trigger_flags']
                 and 'EDGE_BULL' in t['trigger_flags']]

print(f"在阻力位做空 (EDGE_BEAR)      : n={len(at_resistance)}, 胜率={win_rate(at_resistance):.1%}")
```

## 十、重要的技术债务提醒

### 已知但未清理的代码问题

1. **`triggers/bo_retest.go` 中 `BuildLevelsForBoRetest` 和 `buildLevelFromAnchor` 已是死代码**
   这两个函数在 data.go 直接构建 levels 后不再被调用，但仍存在于代码库。
   在下次 refactor 时删除，避免误导。

2. **`triggers/bo_retest.go` 的 BoMaxAgeBars=6 可能过短**
   对于 HTF 级别的支撑突破，回测可能在 30 分钟~2 小时内才出现。
   如果实盘发现 BO_RETEST 确实在发生但未被捕捉，优先调整此参数。

3. **无 portfolio 层面的仓位管理**
   系统每个币独立决策，没有"今日已开3空，不再开更多空单"的限制。
   高相关性下的并发开仓 = 事实上的重仓操作。

4. **HTF_swing 的 R_clean_eval 门槛可能阻止所有 HTF_swing**
   当前要求 R_clean_eval ≥ 1.5 且 Real_R_eval ≥ 2.0，这在震荡市可能永远达不到。
   如果 HTF_swing 出现但全部被 Gate5 拒绝，首先检查这两个阈值。
